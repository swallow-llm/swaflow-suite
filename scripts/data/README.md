# scripts/data: pretraining data pipeline

Builds the tokenized pretraining data together with an order log that records
which documents every training step consumed, without storing any text.

## Overview

```
build config (TOML)       sources, mixture weights, seed, token budget
   |
   |- --stage download    fetch the input files, write the ledger (inputs.json)
   |
   |- --stage tokenize    input files -> uint16 indexed dataset, one shard per file
   |
   '- --stage plan        plan.json (the training order) + heldout/<source>.npz
```

- Every shard is tokenized from exactly one input file and consists of
  `<prefix>.bin` (uint16 tokens; documents concatenated, each followed by EOS),
  `<prefix>.idx` (document offsets and the input row of each document) and
  `<prefix>.meta.json` (source, input file, revision, tokenizer, counts).
- `plan.json` fixes the seed, mixture weights, shard layout and a keyed
  Feistel permutation. The order is a pure function of the plan, so no
  permutation array is stored.
- About 0.1% of the blocks of each source are held out and never reach
  training; the first of them are materialised in `heldout/<source>.npz` for
  validation.

Inputs may be parquet or JSON Lines (`.jsonl`, `.jsonl.zst`, `.jsonl.gz`).
Dolma 3 Mix is distributed as `.jsonl.zst`, which is read with the Python 3.14
standard library (`compression.zstd`).

## Environment

- `SWAFLOW_DATA_ROOT`: output root; a build lands in `$SWAFLOW_DATA_ROOT/<build name>/`
  (or pass `--root`).
- `SWAFLOW_TOKENIZER_DIR`: directory containing `tokenizer.json`
  (SmolLM2-135M, V = 49,152). It overrides `[tokenizer] path` in the configs,
  which is site-specific.
- `SWAFLOW_MMAP_MAX_OPEN`: maximum number of shard mmaps open per process
  (default 1024).
- `HF_HOME`: the Hugging Face cache, where downloaded input files are kept.

## Building

```bash
CFG=scripts/data/configs/dolma3_mix.toml

# 1) download (needs network access)
python -m scripts.data.tokenize_corpus --config $CFG --stage download --allow-design-only

# 2) tokenize; on a single node this also builds the plan and the held-out set
python -m scripts.data.tokenize_corpus --config $CFG --stage tokenize --allow-design-only
```

Both stages are idempotent: completed downloads hit the cache and completed
shards (those with a `.meta.json`) are skipped, so an interrupted job resumes
with the same command. `--stage plan` rebuilds only `plan.json` and the
held-out set from existing shards; `--stage all` runs everything.

On several nodes, run the download and tokenize stages on every node with
`--node-rank r --n-nodes N` (files are assigned round-robin), merge the
per-node ledgers with `--merge-inputs --n-nodes N` after the download, and
run `--stage plan` once after all nodes have finished tokenizing. The launch
scripts show the full sequence.

`dolma3_mix.toml` sets `design_only = true`, so `tokenize_corpus` refuses to
process it unless `--allow-design-only` is given.

## Configs

- `configs/dolma3_mix.toml`: the full Dolma 3 Mix build, every file of the
  pinned dataset revision.
- `configs/dolma3_1b_val.toml`: a 1B-token validation slice (the first file
  of each of the 163 partitions, truncated at document boundaries).

Both are generated by `make_dolma3_config.py` (the selection rule is in its
docstring; the full config uses `--all-files`); do not edit them by hand.

```bash
python -m scripts.data.make_dolma3_config \
    --revision 689a3ea2d8217e64d73a5058913fa43ad15e81aa \
    --target-tokens 1000000000 --out scripts/data/configs/dolma3_1b_val.toml
```

Adding a source needs no code change: add a `[[sources]]` block with
`repo_id` (Hugging Face dataset) or `local_dir`, a `files` glob or list,
`text_column` and `id_column`. Mixture weights are relative and normalised
over all sources.

## Training

The training side reads a build with

```toml
[training]
dataset = "indexed"
dataset_path = "<build dir>"
```

(`torchtitan/models/swaflow/indexed_data.py`). At startup the dataloader writes
`run_order.json` into the run's dump folder: the build, the plan checksum, the
global batch size and the slot convention.

## Order log

Rank r of W data-parallel ranks reads slot `i*W + r` for its i-th sample, so
step t consumes slots `[t*B, (t+1)*B)` for global batch B. `order_log.py`
expands any step or checkpoint into (source, input file, revision, row):

```bash
# summary of the data consumed up to checkpoint step 1000
python -m scripts.data.order_log --build <build dir> \
    --run <dump folder>/run_order.json --checkpoint 1000

# one step, down to individual documents
python -m scripts.data.order_log --build <build dir> \
    --global-batch 64 --step 42 --documents
```

`verify_order.py` runs three checks:

- `roundtrip`: for one step, the tokens yielded by the dataloader equal the
  blocks resolved through the plan and the shards, and equal the referenced
  input rows re-read and re-tokenized from the original files.
- `shuffle` (rebuild): rebuilding the plan with the same seed reproduces
  `plan.json`, the order digest and the held-out files exactly.
- `heldout`: over the whole plan, no held-out block appears in a training slot.

```bash
python -m scripts.data.verify_order --build <build dir> \
    --run <dump folder>/run_order.json --step 1234 --checks all
```

The checks were validated on the 1B-token build (`configs/dolma3_1b_val.toml`).

## SFT data

`build_sft.py` builds SFT blocks with a clean prompt and a noised, scored
response, from Dolci (`--source dolci`) or TinyGSM (`--source tinygsm`).
The design choices are in its docstring; see `--help` for the options.

```bash
python -m scripts.data.build_sft --source dolci --repo <snapshot dir>/data \
    --out $SWAFLOW_DATA_ROOT/dolci_sft_2048 --tokenizer $SWAFLOW_TOKENIZER_DIR
```
